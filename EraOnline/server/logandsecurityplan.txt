  One important caveat: no secret embedded in a client is truly safe from reverse engineering. You should assume a determined attacker can eventually recover it. So this mechanism is useful as a bot/friction filter and signal source, not as a cryptographic proof of
  legitimacy. It still has real value for a game server if you treat it that way.

  Invalid Client Design
  Add invalid_client as a top-level event category.

  What it should mean:

  - the client failed the official-client attestation step
  - the client omitted the required proof
  - the proof was malformed, expired, replayed, or bound to the wrong build/session

  Recommended sub-reasons:

  - missing_attestation
  - bad_attestation
  - expired_attestation
  - replayed_attestation
  - build_mismatch
  - unknown_client_id

  Important design note:

  - do not rely on a single static shared secret in the binary if avoidable
  - better is a challenge/response tied to session/build/version
  - still assume reverse engineers can recover enough to emulate it eventually

  So treat invalid_client as:

  - very useful for filtering mass scanners, crude bots, protocol fuzzers, and off-the-shelf fake clients
  - not sufficient alone to define “official client” against a determined adversary

  - reconnect floods
  - version mismatch spam

  How To Treat invalid_client Specifically
  Recommended enforcement:

  - single invalid_client: deny connection, log only
  - repeated missing_attestation: short cooldown or throttle
  - repeated bad_attestation: short ban candidate
  - replayed_attestation: high-confidence hostile, escalate faster
  - invalid_client plus protocol_error burst: strong ban signal
  - invalid_client plus auth_fail spray across accounts: strong ban signal

  Reasoning:

  - some invalid-client hits may come from stale dev clients or version drift
  - repeated or replay-style failures are much more hostile than one miss
